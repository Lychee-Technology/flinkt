# Kotlin Compiler Compatibility

Flinkt supports **Kotlin 2.4.0 and later** as the compiler for code that uses it. Earlier compilers are unsupported. This page defines what that means, what CI tests, what Flinkt can and can't enforce, and which state guarantees don't depend on the compiler at all.

Kotlin support is independent of the Flink line. Every Flink adapter supports the same Kotlin versions, and adding or dropping a Flink line doesn't change them ([Flink version compatibility](flink-compatibility.md)).

## Policy summary

1. The minimum supported Kotlin compiler is 2.4.0. It applies to every compilation that uses a Flinkt API or runs `flinkt-ksp`.
2. Kotlin 1.x and 2.0 through 2.3 are unsupported. Flinkt has no fallback code for them, and neither CI nor contributors compile, probe or test with them. A question about how an older compiler behaves is out of scope, not open.
3. A Kotlin release later than the newest tested one isn't supported until a reviewed pull request adds it and CI passes with it, including the key-hash pins. Pre-releases (Beta, RC) are never supported.
4. `flinkt-ksp` warns when a compilation's language version is below 2.4. That is the only form of the compiler requirement that the processor can see, and it's a warning, not an error, because it can't tell an unsupported compiler from a supported one set to an older language version ([Enforcement and its limits](#enforcement-and-its-limits)).
5. Serializer compatibility doesn't depend on the compiler. Key identity does, which is why a Kotlin upgrade has to pass the key-hash pins before Flinkt lists it.

## Support table

Status as of November 11, 2026. Flinkt has no build or release yet, so it claims no Kotlin version as tested. The table records the target range and what has been measured so far.

| Kotlin compiler | Status | Evidence so far |
|---|---|---|
| 1.x, 2.0.x to 2.3.x | Unsupported | Kotlin 1.4.32 is historical evidence that the generated `hashCode()` can change ([below](#historical-evidence-kotlin-1432)) |
| 2.4.0 | Minimum supported target. CI tests it once the build exists ([#4](https://github.com/Lychee-Technology/flinkt/issues/4)) | Key hashes and key groups measured |

When the build exists, the table lists the minimum and the newest tested release as pinned versions. A supported release is any stable release between them, each of which has passed the key-hash pins ([What CI tests](#what-ci-tests)).

## Four kinds of compatibility

They answer different questions, and passing one doesn't prove another.

- **Compiler compatibility.** Does code that uses Flinkt compile, and does `flinkt-ksp` run, under this compiler? CI tests it on the minimum and the newest tested version ([What CI tests](#what-ci-tests)).
- **Binary compatibility.** Can this compiler read Flinkt's published classes, and does the application's runtime satisfy them? Flinkt is compiled by its pinned build compiler, with language and API version 2.4 on published modules. Its classes therefore carry Kotlin metadata version 2.4.0 even when the build compiler is newer, and they call no standard-library API newer than 2.4, so a 2.4.0 `kotlin-stdlib` is enough at runtime. Flinkt's own public API is a separate contract, checked by API dumps ([Flinkt API compatibility](testing.md#flinkt-api-compatibility)).
- **Serializer compatibility.** Can a job read bytes and snapshots that another build wrote? The format is Flinkt's: generated codecs write each value with explicit `DataOutput` calls ([Generated code and the adapter](architecture.md#generated-code-and-the-adapter)), and snapshots record Flinkt's schema, not compiler output. Changing the Kotlin compiler changes neither, so it doesn't change whether a snapshot resolves as compatible ([Schema evolution](architecture.md#schema-evolution)). Released fixtures record the Kotlin version that built them, so a difference is traceable ([Released serializer fixtures](testing.md#released-serializer-fixtures)).
- **Key identity compatibility.** Does a restored key still find its state? A data class's or value class's `hashCode()` is generated by the compiler that builds the key class, which is the user's compiler, not Flinkt's. Flink derives the key group of a partition key from it, and the heap backend finds state through it ([Keys](architecture.md#keys)). A serializer snapshot compares schemas and can't see it, so **a compatible serializer doesn't mean a compatible key**. A compiler upgrade that changed the formula would move every data-class or value-class key to another key group, with an identical schema and no error ([What a snapshot can't see](architecture.md#what-a-snapshot-cant-see)). Built-in keys are unaffected: their hash codes come from the JDK.

## Key identity across compiler versions

The generated formula is Kotlin compiler behavior, not a documented guarantee. Flinkt therefore treats it as a fact to measure for each version, not as a property of "Kotlin 2.4 and later".

Measured for this policy on JDK 25: key classes covering every eligible component kind were compiled with each compiler, and their hash codes and key groups compared. The key groups come from Flink 2.3.0's `KeyGroupRangeAssignment` at maximum parallelism 128 and 32768, Flink's default lower bound and its upper bound. Every value was identical across Kotlin 2.4.0, 2.4.10, 2.4.20 and 2.4.21, and across language version 2.0 on the 2.4.20 compiler. Some examples:

| Key | `hashCode()` | key group at 128 | key group at 32768 |
|---|---:|---:|---:|
| `BoolKey(true, 1)`, `data class BoolKey(val v: Boolean, val id: Long)` | 38162 | 22 | 24086 |
| `UserKey(1, 2)`, `data class UserKey(val tenant: Long, val id: Long)` | 33 | 29 | 30365 |
| `FloatKey(Float.NaN, 1)` | 2017460225 | 75 | 715 |
| `StringKey("tenant-a", 1)` | -1852828733 | 71 | 16839 |
| `UserId(42)`, `@JvmInline value class UserId(val value: Long)`, boxed | 42 | 29 | 28189 |

The other kinds measured were `Byte`, `Short`, `Int`, `Long`, `Double` (including `-0.0`) and `Char` components, a data class with one component of every built-in kind, a nested data class, a generic data class and a data class with a value-class component. Kotlin 2.2.21, 2.3.21 and 2.5.0-RC gave the same values too. That is an observation about those builds, not a support claim.

The rules that follow:

- **A Kotlin version is listed as tested only after the key-hash pins pass with key classes compiled by it** ([#32](https://github.com/Lychee-Technology/flinkt/issues/32), [Comparator and key semantics](testing.md#comparator-and-key-semantics)). The pins are constants. A version that produces a different value fails them, and nobody updates the constants to make it pass.
- **A version whose generated `hashCode()` differs is not a safe upgrade for keyed state.** It isn't added to the tested range. If Kotlin ever changes the formula, the pull request that finds it records the version here as unsupported for jobs with keyed state under a data-class or value-class key, with the measured difference, and the release notes say so. Flinkt never presents such an upgrade as compatible because the serializer snapshot still resolves.
- Upgrading Kotlin between two tested versions keeps every key in its key group. Upgrading to a version outside the tested range is untested for key identity, whatever its serializer compatibility.

### Historical evidence: Kotlin 1.4.32

Compiled by Kotlin 1.4.32, a `Boolean` component contributes 1 or 0 to a data class's hash, where 2.4.20 uses `Boolean.hashCode()`, 1231 or 1237. `BoolKey(true, 1).hashCode()` is 32 on one and 38162 on the other, on the same JDK (measured in the [#33 review](https://github.com/Lychee-Technology/flinkt/pull/33#issuecomment-5975253307)). It shows that the formula has changed before, for a component kind on the eligible list. That is why each version is measured and why the pins include a `Boolean` key. It doesn't make 1.4.32 a target. Flinkt doesn't compile anything with it, and the pins assert the supported compilers' value, 38162, which a compiler with the 1.4.32 formula fails.

## What CI tests

Two compilers, not a matrix. Both versions are pinned in a committed file, as Flink versions are, and no lane resolves a dynamic version such as `2.4.+`.

- **The build compiler** is the newest tested 2.4.x or later release. It builds Flinkt, and every suite runs on it.
- **The minimum, 2.4.0,** compiles the code that stands for user code against Flinkt as built: KSP compilation and negative compilation tests, the key classes of the hash pins, and the integration job. That catches a published API, a generated source or a processor behavior that needs a compiler newer than 2.4.0.

Which tier runs what is in [CI tiers](testing.md#ci-tiers). Releases between the two pinned versions don't each get a lane. They get the hash pins once, when they enter the range, and the range is narrowed if one is found to differ.

Adopting a new Kotlin release is a reviewed pull request that moves the pinned build compiler and passes every lane, the hash pins included, before Flinkt claims it as tested. The same pull request runs the hash pins with every stable release between the previous build compiler and the new one, so no release in the range is unmeasured. A scheduled job may notice the release and open that pull request, but it never changes what CI tests on its own. Raising the minimum is a policy change made here, with its reason.

**KSP.** KSP versions don't follow Kotlin versions any more. KSP 2.3.12 and 2.3.13 ran a probe processor and compiled its generated code with the Kotlin Gradle plugin at 2.3.21, 2.4.0, 2.4.20, 2.4.21 and 2.5.0-RC. Flinkt pins one KSP version in its build and tests the processor with it, and the support table names it once the build exists. Other KSP versions are untested.

## Enforcement and its limits

Flinkt can stop or warn about most unsupported compilers, but it can't prove which compiler built a user's class. Three mechanisms exist, and each has a gap.

- **Kotlin metadata.** Flinkt's classes carry metadata version 2.4.0. Kotlin 2.2.21 refuses to compile against them ("The binary version of its metadata is 2.4.0, expected version is 2.2.0"), unless the user passes `-Xskip-metadata-version-check`. Kotlin 2.3.21 compiles against them without an error or a warning, because a compiler reads metadata one version ahead. So metadata stops 2.2 and earlier, not 2.3.
- **Gradle.** Gradle module metadata can't express a requirement on the consumer's Kotlin compiler. Flinkt's dependency on `kotlin-stdlib` raises the application's standard library, not its compiler.
- **The KSP processor.** Under KSP2, `SymbolProcessorEnvironment.compilerVersion` reports the Kotlin version bundled with KSP, 2.4.20 for KSP 2.3.12 and 2.3.13, whatever compiler the build uses. It reported 2.4.20 with the Kotlin Gradle plugin at 2.3.21, 2.4.0, 2.4.21 and 2.5.0-RC alike, so it can't enforce anything. `kotlinVersion` reports the compilation's language version, so `flinkt-ksp` emits a warning when it's below 2.4, naming this policy. That flags a 2.3 compiler at its default language version. It doesn't flag a 2.3 compiler given `-language-version 2.4`, which Kotlin 2.3.21 accepts with a warning that the language version is experimental. It's a warning rather than an error because a supported 2.4 compiler set to a lower language version would trigger it too, and language version 2.0 on 2.4.20 produced identical key hashes. Failing those builds would cost users more than the check is worth. The policy's purpose is to define what Flinkt supports and tests, not to police every build.

A class's `@Metadata` can't identify its compiler either. Its metadata version follows the language version: 2.4.20 with language version 2.0 writes 2.0.0, and 2.3.21 with language version 2.4 writes 2.4.0.

The warning matters most for keys. Every key class whose hash depends on the Kotlin compiler is a `@FlinkType` data class or value class, so `flinkt-ksp` runs in the compilation that builds it. Built-in keys hash through the JDK. A build that ignores the warning, or a key class built by an unsupported compiler that claims a supported language version, is outside the policy. The hash pins cover only the compilers CI runs, so nothing would catch a different formula there.

## Open questions

- **A runtime formula check.** Generated code could compare a key's `hashCode()` with the formula Flinkt expects, over the key's own components, when the view's `keyBy` or `runtimeContext.mapState` checks eligibility. That would catch a compiler with a different formula whatever version it reports. It adds generated code to every key type and hasn't been decided.
