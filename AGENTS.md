# AGENTS.md

## Project state

**Flinkt** is in the design stage. It has a build, `flinkt-core`'s type model, codec SPI and generated-type registry, the adapters' `typeInfo<T>()` for Flink's built-in types, `flinkt-view-codegen`, which generates view forwarders, and the views (`.flinkt()`, `asFlink()`, hand-written `map`, `keyBy` and keyed `process`, and the first slice's forwarded methods), but no state helpers or Flinkt serializers yet. The repository contains:

- the user-facing design (`README.md`);
- the architecture decisions and their reasons (`docs/architecture.md`);
- the schema-evolution decision record (`docs/schema-evolution.md`);
- the persisted-format decision record: record and snapshot bytes, and restore (`docs/persisted-format.md`);
- the Flink version policy (`docs/flink-compatibility.md`);
- the Kotlin compiler policy (`docs/kotlin-compatibility.md`);
- the test strategy (`docs/testing.md`);
- the build: modules, toolchain, pinned versions, build checks and CI lanes (`docs/build.md`);
- contributor rules (`docs/non-code-rules.md`).

The Gradle build has the planned modules, `flinkt-core`, `flinkt-ksp`, `flinkt-view-codegen`, `flinkt-flink23` and `flinkt-flink120`, plus the internal `test-support`. Apart from `flinkt-core`, `flinkt-view-codegen`, and the adapters' `typeInfo<T>()`, views and `@ExperimentalFlinkApi`, their production code is only what the build checks need. There's no linter or formatter.

Read `README.md` and `docs/architecture.md` before you propose or write code. Read `docs/persisted-format.md` and `docs/schema-evolution.md` before you touch a persisted format, a serializer snapshot or restore. Read `docs/flink-compatibility.md` before you change Flink-facing code or the support matrix. Read `docs/kotlin-compatibility.md` before you change the Kotlin or KSP version, the language or API version, or the key-hash checks. Read `docs/testing.md` before you add tests or CI. It defines the evidence that each compatibility claim needs. Read `docs/build.md` before you change the build, a pinned version, the module layout or the CI lanes.

Each rule has one canonical home, and the summary below links to it. When a rule changes, change it there and update this file's summary.

## Build and test

Gradle, through the wrapper. A machine without JDK 17 gets one automatically (Foojay).

```sh
./gradlew build                                            # compile, test and check every module and the build logic
./gradlew :build-logic:test                                # the build logic's own tests
./gradlew :flinkt-core:test                                # one module's tests
./gradlew :test-support:test --tests 'io.flinkt.testing.compile.KotlinCompilationTest'   # one test class
./gradlew :test-support:test --tests '*KotlinCompilationTest.warnings*'                  # one test method
./gradlew :flinkt-flink120:test --tests 'io.flinkt.flink.AdapterCompileTest'             # a shared adapter test on one line
./gradlew updateKotlinAbi                                  # rewrite the ABI dumps after an intended API change
./gradlew :flinkt-flink23:extractFlinkApi                  # rewrite an adapter's flink-api.tsv after a Flink version change
```

PR CI runs two lanes ([build.md](docs/build.md#pr-ci)): `./gradlew build -x :flinkt-flink120:check`, and `./gradlew :flinkt-flink120:check -Pflinkt.test.excludeTags=minicluster`.

- **Versions** are pinned in `gradle/libs.versions.toml`: JDK 17, Kotlin 2.4.21 as the build compiler, 2.4.0 as the minimum, KSP 2.3.13, Flink 2.3.0 and 1.20.5, and 2.2.1 for the 2.3 adapter's `flink22FormatTest`, which runs the record format's evidence on 2.2 until #27 adds its adapter. No dynamic selectors. ([build.md](docs/build.md#pinned-versions))
- **Published classes** target Java 8, because Flink 1.20 still runs on it, and compile with language and API version 2.4 against `kotlin-stdlib` 2.4.0. ([build.md](docs/build.md#toolchain))
- **Adapters** compile `adapters/shared/src` plus their own `src`, which holds only what can't compile on another line. Flink is `compileOnly`, and the line's Flink is on the test classpath. ([build.md](docs/build.md#adapters))
- **`check` fails** on a public ABI that differs from the module's `api/*.api` dump, on a declaration without explicit visibility in a published module, on an adapter's `flink-api.tsv` that isn't what `extractFlinkApi` reads from its Flink jars, and when `checkDependencyBoundaries` finds Flink in `flinkt-core` or on a published runtime classpath, or `flinkt-ksp` or `flinkt-view-codegen` on one. A file dependency fails every boundary on its classpath, because it has no coordinates to check. ([build.md](docs/build.md#dependency-boundaries))
- **Compile tests** use `:test-support`: `exactTypeOf(x).shouldBe<T>()` for exact static types, and `KotlinCompilation(KotlinCompiler.BUILD or MINIMUM).compile(code)` with `assertSuccess()` or `assertFailure(...)` for code that must or mustn't compile, optionally with a KSP processor. Match diagnostic names and the wording both compilers share. Don't build another harness. ([build.md](docs/build.md#compile-test-harness))
- **View forwarders** come from `flinkt-view-codegen`, which each adapter runs through KSP with its checked-in `flink-api.tsv` and the Flink version on its compile classpath. Its tests are adapter tests, so both lanes run them, and a test that only holds on one line goes in that line's `ViewCodegenLineTest`. `CrossAdapterForwardersTest` compares every adapter's generated forwarders, parameter names and `@Deprecated`/`@ExperimentalFlinkApi` included, and fails on a difference between lines that its per-line list doesn't hold as generated, packages and body included. Changing a forward list means `updateKotlinAbi` and, for a difference between lines, that list. ([build.md](docs/build.md#view-forwarders))
- **Tag a MiniCluster test** `@Tag("minicluster")`. The 1.20 PR lane skips it.

## Architecture (planned)

Flinkt is a Kotlin-first layer over Apache Flink APIs. It has three layers: a KSP processor used only at build time, a Flink-free core (`@FlinkType`, the type model, the generated-codec SPI, the persisted-schema model and the compatibility planner), and one adapter per Flink minor line. They're separate because each changes on its own timescale. Generated source is cheap to replace, but a serializer format that users have already written into checkpoints is not. Modules and their reasons: [architecture.md](docs/architecture.md#layers-and-modules).

**Streams are views.** `.flinkt()` wraps a Flink `DataStream`, `SingleOutputStreamOperator`, or `KeyedStream` in `FlinktDataStream`, `FlinktSingleOutputStreamOperator`, or `FlinktKeyedStream`. The view holds that one object and never constructs a Flink stream object. `asFlink()` returns the same instance. Each view method calls the Flink method of the same name, once, on the held object, and wraps what that call returned. Keyed `process` is the one method with a second call: Flink's `process(fn, TypeInformation)` is `@Internal`, so the view calls `process(fn)` and then `returns(typeInfo<R>())` on the object that returned, before anything reads its type. Operators that introduce an element type take Flink's function type, reify the result type from the call site, and pass `typeInfo<R>()` to Flink through a public Flink method. Those are hand-written. Until #32 implements the key rules, the view's `keyBy` accepts only the non-null built-ins, and its `TypeInformation` overload only Flink's `BasicTypeInfo` for them, and it refuses every other key type before it calls Flink. Every other view method only forwards and is generated by `flinkt-view-codegen` (KSP, Flinkt's own build only) from the Flink classes of the adapter's line. Forwarders keep Flink's overloads, parameter names (from a checked-in file read from Flink's class files), deprecations, and `@Experimental` status (as the `@ExperimentalFlinkApi` opt-in). The generator fails the build on a method that would break a view rule. The first slice forwards fluent configuration, `filter`, `union`, repartitioning, `assignTimestampsAndWatermarks` and the sinks and terminal calls, and never `enableAsyncState()`: Flink 2.x's async state is out of scope for #31 ([forward lists](docs/architecture.md#the-first-slices-forward-lists)). A Flink method the view doesn't offer is reached through `asFlink()` and is a compile error on the view. User-facing rules: [README](README.md#flinkt-streams). Implementation rules: [architecture.md](docs/architecture.md#views).

**State helpers.** `valueStateDescriptor<T>()`, `listStateDescriptor<T>()`, and `mapStateDescriptor<K, V>()` return Flink descriptors. `runtimeContext.valueState<T>()`, `listState<T>()`, and `mapState<K, V>()` bind state in `open()` and return Flink's `ValueState`, `ListState`, and `MapState`. See [README, State](README.md#state).

**Type model and registry.** `TypeRegistry.load(classLoader)` builds a registry from the `GeneratedTypeModule`s that `ServiceLoader` finds through that class loader. `model(kType)` analyzes any `KType` into a `FlinktType` that keeps every argument and `?`, and `resolve(model)` resolves the shapes a release supports, with its own registry's declarations whichever registry built the model, and throws `UnsupportedTypeException`, naming the canonical type, for the rest. A built-in resolves to its `BuiltInKind`, which the adapter maps to Flink's own `TypeInformation`, and a generated record to its codec. Generated types are identified by their `Class`, never by name, and nothing is cached in a static field. A platform type is modeled as non-null. Core writes no bytes, scalars included, and no module can register a codec for a built-in. See [architecture.md](docs/architecture.md#type-model-and-registry).

**Type information.** `typeInfo<T>()` resolves `typeOf<T>()` with a registry loaded, on each call, from the thread's context class loader. A non-null built-in gives Flink's own `BasicTypeInfo` for its boxed JVM class, so its serializer and bytes are Flink's. Every other type, generated types included until #12, throws `UnsupportedTypeException` naming the full Kotlin type and the two fixes, and never falls back to `TypeExtractor` or `GenericTypeInfo`. A generated type fails before its codec factory runs, and its message says its annotation gives it no `TypeInformation` yet. Each further built-in mapping, such as `BigDecimal` or `Instant`, fixes a state format, so it's its own change with its reason. See [architecture.md](docs/architecture.md#type-information).

**Generated code** implements the Flink-free codec SPI and never subclasses a Flink class. KSP also generates each record type's persisted schema and a migration constructor. Each adapter owns the `TypeInformation`, `TypeSerializer`, and snapshot classes shared by all generated types, and the snapshot class, `io.flinkt.flink.FlinktSerializerSnapshot`, has the same name on every adapter. Decoding, `copy` and the migration constructor rebuild a record through its primary constructor, so an `init` block may check its arguments but must not change a constructor property, its own class's or a component's, and every value that's written or copied must pass those checks, also after a `var` was assigned. KSP can't see `init` blocks, so for values that's a documented contract, not a compile error, and users get a byte-comparing round-trip check to run in their tests ([Rebuilding through the constructor](docs/architecture.md#rebuilding-through-the-constructor)). See [architecture.md](docs/architecture.md#generated-code-and-the-adapter).

**Schema evolution.** Records are compact, and the snapshot carries a symbolic, recursive schema. A Flink-free planner in `flinkt-core` compares the old and current schemas and gives one plan, which both `resolveSchemaCompatibility` and the old-layout serializer that `restoreSerializer()` returns use. See [schema-evolution.md](docs/schema-evolution.md#restore-model).

**Persisted format.** Decided in #5, not implemented: record format version 1 and snapshot format version 1. A record is a null bitmap, if it has nullable fields, then its fields in ascending `String.compareTo` order of their property names. It has no header, and nested records are inline. The bitmap is `ceil(n / 8)` bytes, least significant bit first, and a set bit means null. Scalars are fixed-width big-endian. A `Float` or `Double` is written as `floatToIntBits` or `doubleToLongBits` through `writeInt` or `writeLong`. A `String` is in Flink's `StringValue` char-varint format, specified as Flinkt's own. Each field has the bytes that Flink's own serializer for its type writes on a `DataOutputSerializer`. A nullable value outside a record field is a `00` or `01` marker, then the value. The snapshot is a binary schema graph: the record format version, the key role, the root type, and each reachable declaration once, sorted by name, with fields in constructor order and enum and sealed IDs in ascending order. Readers are strict: after the clear bit of a field declared `T?`, a nullable argument's marker is `01`, never `00`. They're bounded: a `String` has at most 2^26 chars and a `List` or `Map` at most 2^26 elements, and writing enforces both. Nothing is allocated from a count, an object or a record without fields is never a field, an element or a type argument, so every loop consumes input, and schema checks never recurse past 64 levels. `restoreSerializer()` throws the planner's diagnostic for an incompatible plan, a missing type or an unknown version, and never returns a serializer that misreads. The prototype in `adapters/shared/src/test/kotlin/io/flinkt/flink/format` is evidence, not production code. See [persisted-format.md](docs/persisted-format.md).

**Decided type forms.** Collections are `List` and `Map` only. They use one Flinkt-owned encoding as a field and as a top-level type: size, then elements or entries in iteration order. `Set`, `Collection`, the mutable interfaces and arrays fail explicitly, and so does a `Map` key type that has, at any depth, a hand-written `equals()` or `hashCode()`, a data class with a `var` constructor property, or a collection. A `Map` value whose runtime class isn't one of the hash-based maps that the JDK and Kotlin's factories build fails when it's written or copied, because only its entries are persisted. Enum constants and sealed subtypes carry `@FlinkId`, a positive `Int` written as 4 big-endian bytes, and each nested sealed level has its own ID namespace. An enum constant or object subtype is written as its ID alone, so an object subtype holds no stored state and an enum no `var`. A codec's bytes never depend on the output view it writes to. See [architecture.md](docs/architecture.md#persisted-formats).

**Kotlin compiler.** The minimum supported compiler is Kotlin 2.4.0, for every Flink adapter alike. Earlier versions are unsupported and get no fallback code. A later release is supported only after CI passes with it, including the key-hash pins and formula checks, because a key's `hashCode()` comes from the compiler that builds the key class and a serializer snapshot can't see it. CI uses two compilers, the pinned build compiler and 2.4.0, not a matrix. Kotlin 1.4.32 is historical evidence of a formula change, not a target. **Don't spend effort on Kotlin before 2.4.0:** don't compile, probe or test with it, and don't add evidence, fixtures or fallbacks for it. `flinkt-ksp` only warns about a language version below 2.4, because KSP2 can't report the real compiler. See [kotlin-compatibility.md](docs/kotlin-compatibility.md).

## Invariants

Code and reviews are held to these rules. Each link goes to the canonical text:

- **Flink stays recognizable.** Use Flink's operator names, and keep UIDs, parallelism, `ProcessFunction`, `TypeInformation`, and `TypeSerializer` visible. State is bound in `open()`. ([README](README.md#keep-flink-recognizable))
- **No silent Kryo.** A type Flinkt can't model fails explicitly, and generic serialization is opt-in only. ([README](README.md#make-unsupported-types-explicit))
- **No reflection on the per-record path**: serialize, deserialize, copy, field access, or comparison. Also avoid `Array<Any?>`-style serializers. Migration during restore may be slower and may use temporary field slots, but it constructs values through generated constructors and never reflects. ([README](README.md#generated-serializers), [schema-evolution.md](docs/schema-evolution.md#cost))
- **Keep the full Kotlin type**, including nested generic arguments and nullability. `T::class.java` is not enough. ([README](README.md#generic-types))
- **Stable identity.** Every enum constant and sealed subtype declares an explicit `@FlinkId`. Identity never comes from declaration order, ordinal or name, and an unknown ID fails the read. A name that the old snapshot had under another ID, as in an ID swap, is incompatible. ([README](README.md#sealed-types-and-enums), [architecture.md](docs/architecture.md#enum-and-sealed-identity))
- **Explicit state compatibility.** The target for ordinary values is `PojoSerializer`-level evolution: an identical schema, or a pure reorder outside a `keyBy` key, is compatible as-is; a removed field, and an added field with a defined migration default, migrate, recursively through nested records, `List` elements and `Map` values; a field type change, a class rename and an added field without a legal default are incompatible. Each migration stays incompatible until its stage lands with old-bytes and backend evidence. Snapshots record a symbolic, recursive schema, never a hash, so the old layout can be read without the old classes. There's no `compatibleWithReconfiguredSerializer` and no per-role snapshot class. ([schema-evolution.md](docs/schema-evolution.md), [README](README.md#schema-and-state-compatibility), [testing.md](docs/testing.md#serializer-snapshot-compatibility))
- **Keys are proved, not assumed, and never migrate.** Serializable doesn't mean a safe key, and a compatible serializer doesn't mean a compatible key. A structural change to a persisted key, or under a `Map` key, is incompatible even when the same change migrates a value, and the map-state helpers and the view's `keyBy` record the key role in the snapshot so a restore can tell. A constructor reorder in a `keyBy` key is incompatible too, because the generated `hashCode()` follows constructor order. `keyBy` partition keys, keyed `MapState` user keys and broadcast-state keys have separate rules. `keyBy` accepts only non-null built-ins, and value and data classes whose `equals()` and `hashCode()` are compiler-generated, whose constructor properties are `val`s, and whose components are all eligible. Enums, objects, sealed types, collections and nullable keys are rejected there. A `TypeInformation` Flinkt didn't build, or `asFlink()`, opts out of Flinkt's key checks. ([README](README.md#keys), [architecture.md](docs/architecture.md#keys), [schema-evolution.md](docs/schema-evolution.md#keys))
- **Views change nothing Flink sees.** Never construct a Flink stream object or read the type of a stream a view wraps. Call only public Flink methods. ([architecture.md](docs/architecture.md#views))

Still undecided, so don't present these as settled: [Open questions](docs/architecture.md#open-questions), which are the value-class representation and migration defaults for added fields. [schema-evolution.md](docs/schema-evolution.md#open-decisions) lists what the old-layout serializer still has to settle.

**First milestone.** `@FlinkType data class User(val id: Long, val name: String)`, then `.flinkt().map { User(...) }.name(...).keyBy { it.id }.process(...)` with `runtimeContext.valueState<User>("user")`, with serializer snapshots restoring state correctly. It is built against Flink 2.3 first, and the adapter source also compiles against 1.20 in PR CI. See [README](README.md#initial-implementation-boundary) and [testing.md](docs/testing.md#pull-requests).

## Non-code artifacts

Issues, PR descriptions, design docs, plans, and reviews follow `docs/non-code-rules.md`. The main points:

- Write for a reader who wasn't in the session. Cover the why, the outcome, the judgment calls, the risks, and what reviewers should focus on.
- Record reasoning, not a narrated diff. Never invent measurements or decisions.
- Every artifact must end up on GitHub, in English. Issue and PR descriptions are the issue or PR body. Post any other artifact in full as a comment on the relevant PR or issue, and say what kind of artifact it is. A file path or summary doesn't count.
- Durable decisions such as ADRs and runbooks go in `docs/`.

Blog posts in `docs/blog/` also follow `docs/blog/AGENTS.md`, which doesn't exist yet.
